Much of the dynamics can be modeled, but it is hard to get right and hard to make fast.

Most of what moves a satellite is known physics: the gravity field, drag, radiation pressure, third bodies, tides, relativity. Then everything has to be evaluated in the right time system and the right frame, which is where subtle bugs live. Click: the point of the slide. Modeling these is possible, but it is hard to get right and hard to make fast, and that is the job of an astrodynamics library.

brahe aims to be for astrodynamics what numpy is for arrays: the common, dependable layer you build on without thinking about it. The four properties come back, and the goal is all four at once. Developed since 2014, MIT licensed, a Rust core with Python bindings, and it runs on Linux, macOS and Windows. One pip install. The rest of the talk is evidence for each check mark: modules (capable), benchmarks (fast), short scripts (easy), and every script is public (open).

The modules in brahe

A quick tour, left to right. Time: epochs and conversions between UTC, GPS time, TAI and TT. Frames and coordinates: inertial and Earth-fixed frames with Earth orientation data, geodetic and topocentric coordinates. Orbits: element sets, TLEs, Walker constellations. Propagation: SGP4 and numerical propagation with configurable force models. Access: when can a station or satellite see another object, under which constraints. Data clients: CelesTrak, Space-Track, IGS orbit products. Estimation: extended and unscented Kalman filters and batch least squares. This row comes back as a divider, with the module in use lit up.

Design choices in brahe

SI units everywhere

Meters, seconds and kilograms in and out of every function. Angles take an explicit degrees or radians argument.

Composable pieces

Propagators, force models, access constraints and event detectors are separate objects that you combine.

Compiled core with Python bindings

The numerical work runs in compiled Rust, called from Python.

Every documentation example runs

Each example in the documentation is compiled and run on every commit, so the docs match the code.

Four choices that make the library usable as a dependency. SI units everywhere: no guessing whether a function wants kilometers. Planned remark: "SI everywhere. \( \rho \) is the sum of the first three rows; positive terms lengthen the pseudorange. A satellite clock ahead of GPS time (\( dt_s > 0 \)) shortens it. The receiver clock \( c\,dt_r \), the ionosphere and the troposphere are not modeled.

The same station and satellite as the time-system slide, at the reference instant, 19:00 GPS time (18:59:42 UTC), taken as the reception time, with the modeled pseudorange P = rho + c (dt_r - dt_s) built one term at a time. The first three rows add up to rho, the range including the signal travel time. Geometric range at the reception time: about twenty thousand kilometers. Click: the satellite moves during the roughly 67 ms the signal is in flight, which changes the range by meters. Click: the Earth turns under the signal (Sagnac), sub-meter here because the satellite is near zenith; it reaches tens of meters at low elevation. Click: the satellite clock offset from the IGS clock product. This satellite's clock reads ahead of GPS time, so the term is negative: the signal appears to arrive sooner. It is enormous in meters, which is why every receiver solves for clocks. All of this is a few lines with brahe states; brahe has no pseudorange function, so the script computes these terms directly.

Detect an event defined by any function of the state

snippets/value_event.py · after brahe examples/numerical_propagation/custom_value_event.py

A ValueEvent watches any function of the epoch and state and records when it crosses a target value in a chosen direction. Here it is the z component of position crossing zero going up: the ascending node. The propagator refines the crossing time and keeps going. The same mechanism covers altitude thresholds, eclipse entry and exit, element values, and events with callbacks that change the state, such as maneuvers.

Sensitivity of the state to spacecraft parameters

snippets/sensitivity.py · after brahe examples/numerical_propagation/sensitivity_analysis.py

Turn on sensitivity and the propagator integrates the partial derivatives of the state with respect to the spacecraft parameters (mass, drag area, drag coefficient, SRP area, reflectivity), which is what consider covariance analysis in estimation needs. The program prints how far the position moves after one orbit for a 1 percent change in each parameter.

Custom access window properties with a property computer

brahe's access computation currently takes ground locations, so the satellite-to-satellite geometry in the MMS example is computed from propagated states directly.

snippets/property_computer.py · after brahe examples/access/properties/custom_property_computer.py

An access property computer is a small class with three methods: where to sample each window, what to compute from the sampled satellite states and the location, and the names of the properties it returns. brahe calls it for every access window it finds, so any custom quantity (range, Doppler, an antenna angle) arrives attached to the windows. Today the access search takes ground locations; satellite-to-satellite access, which the MMS example needed, is on the list.

brahe has been developed since -- and is tested continuously

Every documentation example runs

Each Rust and Python example in the documentation is compiled and run on every pull request and every change to the main branch. The Rust and Python test suites run on Linux, macOS and Windows.

Tests make extension practical

The existing test suite is what makes LLM-assisted extension and maintenance practical: new code, written by hand or with an LLM, has to pass the same tests and examples.

brahe started in 2014 as research code and has been rebuilt around a Rust core with Python bindings. Two things keep it dependable. Every example in the documentation is real code that is compiled and run in continuous integration, so the docs cannot drift from the library, and the unit tests run on all three operating systems. And the test suite is what makes it practical to extend and maintain the library with LLM assistance: the tests define what correct means, so generated code is checked against the same bar as hand-written code.
