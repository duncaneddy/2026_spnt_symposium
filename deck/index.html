Much of the dynamics can be modeled, but it is hard to get right and hard to make fast.

Most of what moves a satellite is known physics: the gravity field, drag, radiation pressure, third bodies, tides, relativity. Then everything has to be evaluated in the right time system and the right frame, which is where subtle bugs live. Click: the point of the slide. Modeling these is possible, but it is hard to get right and hard to make fast, and that is the job of an astrodynamics library.

Which tool do you use, and which of these did you give up?

Four things you want from an orbit tool: capable (the physics and features you need), fast, easy to use from a script, and open (source you can read, and no license server). Click: ask the question and wait for a few answers. Expected: STK, GMAT, Orekit, MATLAB scripts, "something my advisor wrote". Then one family per click. These are general tendencies, not a review of any one product. Commercial tools (STK, FreeFlyer) are capable and fast, but scripting them is awkward and they are closed and licensed. Research scripts and small open-source packages are open and sometimes easy, but usually limited in scope with uncertain validation. Established open-source toolkits such as Orekit and GMAT are capable and open, with a steeper path to use (Java, a mission scripting language). brahe aims to be for astrodynamics what numpy is for arrays: the common, dependable layer you build on without thinking about it. The four properties come back, and the goal is all four at once. Developed since 2014, MIT licensed, a Rust core with Python bindings, and it runs on Linux, macOS and Windows. One pip install. The rest of the talk is evidence for each check mark: modules (capable), benchmarks (fast), short scripts (easy), and every script is public (open).

The modules in brahe

A quick tour, left to right. Time: epochs and conversions between UTC, GPS time, TAI and TT. Frames and coordinates: inertial and Earth-fixed frames with Earth orientation data, geodetic and topocentric coordinates. Orbits: element sets, TLEs, Walker constellations. Propagation: SGP4 and numerical propagation with configurable force models. Access: when can a station or satellite see another object, under which constraints. Data clients: CelesTrak, Space-Track, IGS orbit products. Estimation: extended and unscented Kalman filters and batch least squares. This row comes back as a divider, with the module in use lit up.

The range from the campus station to G09 over its whole pass. The two epochs differ in one argument: the IGS file's timestamps are GPS time, so the correct epoch says time_system=bh.GPS. The mistake, very common in practice, is building the same calendar time as UTC. brahe does exactly what it is told: a UTC label means the instant 18 seconds later, because GPS time has not taken the leap seconds since 1980. It is smaller than the position error because only the motion along the line of sight changes the range, and it changes sign as the satellite crosses overhead. Nothing crashes and the ranges still look plausible, which is what makes this bug expensive. Planned remark: "18 seconds. NASA's Magnetospheric Multiscale mission flies four spacecraft in a very eccentric orbit; at apogee MMS 1 is almost 28 Earth radii out, about seven times the radius of the GPS orbits. GPS antennas point at the Earth. Up there, the only signals that reach you are the ones that spill past the Earth's limb from satellites on the far side. Drawn exactly: for one GPS satellite, the main lobe to 23.5 degrees off boresight, side lobes out to 70 degrees, and the shadow of the Earth plus 100 km of atmosphere. Ask the question and wait. Click: the replay moves MMS around the orbit and counts the GPS satellites whose line to MMS falls inside the main lobe, and inside the main or side lobes, with the Earth blocking. This is geometry only: no transmit power, gain pattern shape, path loss or receiver sensitivity. brahe's access module takes ground locations, not a second satellite, so the script computes the off-boresight angle directly from brahe states with numpy. Every sample of the orbit, plotted against distance from the Earth's center. Main lobe only: above about 8 Earth radii the count is mostly zero to two, and four or more satellites are available in about 4 percent of the orbit: near perigee, below about 6 Earth radii, and in short windows between about 11 and 17 Earth radii. So the answer is yes, with a careful receiver and a link budget that this plot does not include.

Detect an event defined by any function of the state

brahe example examples/numerical_propagation/custom_value_event.py

A ValueEvent watches any function of the epoch and state and records when it crosses a target value in a chosen direction. Here it is the z component of position crossing zero going up: the ascending node. The propagator refines the crossing time and keeps going. The same mechanism covers altitude thresholds, eclipse entry and exit, element values, and events with callbacks that change the state, such as maneuvers.

Additional state dynamics and consider-parameter sensitivity

Battery charge as an extra state

Sensitivity of the state to spacecraft parameters

brahe examples/numerical_propagation/battery_tracking.py and sensitivity_analysis.py

Two ways to extend the numerical propagator. Left: append your own states to the orbit state and give their derivatives; here a battery that charges in sunlight and drains in eclipse, integrated alongside the orbit with the same integrator (the example also clamps the charge to the battery limits, omitted here). Right: turn on sensitivity and the propagator integrates the partial derivatives of the state with respect to the spacecraft parameters (mass, drag area, drag coefficient, SRP area, reflectivity), which is what consider covariance analysis in estimation needs.

Custom access window properties with a property computer

brahe's access computation currently takes ground locations, so the satellite-to-satellite geometry in the MMS example is computed from propagated states directly.

brahe example examples/access/properties/custom_property_computer.py

An access property computer is a small class with three methods: where to sample each window, what to compute from the sampled satellite states and the location, and the names of the properties it returns. brahe calls it for every access window it finds, so any custom quantity (range, Doppler, an antenna angle) arrives attached to the windows. Today the access search takes ground locations; satellite-to-satellite access, which the MMS example needed, is on the list.

brahe has been developed since -- and is tested continuously

Every documentation example runs

Each Rust and Python example in the documentation is compiled and run on every pull request and every change to the main branch. The Rust and Python test suites run on Linux, macOS and Windows.

Tests make extension practical

The existing test suite is what makes LLM-assisted extension and maintenance practical: new code, written by hand or with an LLM, has to pass the same tests and examples.

brahe started in 2014 as research code and has been rebuilt around a Rust core with Python bindings. Two things keep it dependable. Every example in the documentation is real code that is compiled and run in continuous integration, so the docs cannot drift from the library, and the unit tests run on all three operating systems. And the test suite is what makes it practical to extend and maintain the library with LLM assistance: the tests define what correct means, so generated code is checked against the same bar as hand-written code.
