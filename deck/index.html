Much of the dynamics can be modeled, but it is hard to get right and hard to make fast.

Most of what moves a satellite is known physics: the gravity field, drag, radiation pressure, third bodies, tides, relativity. Then everything has to be evaluated in the right time system and the right frame, which is where subtle bugs live. Click: the point of the slide. Modeling these is possible, but it is hard to get right and hard to make fast, and that is the job of an astrodynamics library.

Which tool do you use, and which of these did you give up?

Four things you want from an orbit tool: capable (the physics and features you need), fast, easy to use from a script, and open (source you can read, and no license server). Click: ask the question and wait for a few answers. Expected: STK, GMAT, Orekit, MATLAB scripts, "something my advisor wrote". Then one family per click. These are general tendencies, not a review of any one product. Commercial tools (STK, FreeFlyer) are capable and fast, but scripting them is awkward and they are closed and licensed. Research scripts and small open-source packages are open and sometimes easy, but usually limited in scope with uncertain validation. Established open-source toolkits such as Orekit and GMAT are capable and open, with a steeper path to use (Java, a mission scripting language). Speed is shown only for commercial tools here; the benchmarks at the end compare brahe with Orekit, GMAT, Nyx and Basilisk directly. Planned remark: "Pick any two. On a good day."

brahe aims to be for astrodynamics what numpy is for arrays: the common, dependable layer you build on without thinking about it. The four properties come back, and the goal is all four at once. Developed since 2014, MIT licensed, a Rust core with Python bindings, and it runs on Linux, macOS and Windows. One pip install. The rest of the talk is evidence for each check mark: modules (capable), benchmarks (fast), short scripts (easy), and every script is public (open).

The modules in brahe

A quick tour, left to right. Time: epochs and conversions between UTC, GPS time, TAI and TT. Frames and coordinates: inertial and Earth-fixed frames with Earth orientation data, geodetic and topocentric coordinates. Orbits: element sets, TLEs, Walker constellations. Propagation: SGP4 and numerical propagation with configurable force models. Access: when can a station or satellite see another object, under which constraints. Data clients: CelesTrak, Space-Track, IGS orbit products. Estimation: extended and unscented Kalman filters and batch least squares. This row comes back as a divider, with the module in use lit up.

Design choices in brahe

SI units everywhere

Meters, seconds and kilograms in and out of every function. Angles take an explicit degrees or radians argument.

Composable pieces

Propagators, force models, access constraints and event detectors are separate objects that you combine.

Compiled core with Python bindings

The numerical work runs in compiled Rust, called from Python.

Every documentation example runs

Each example in the documentation is compiled and run on every commit, so the docs match the code.

Four choices that make the library usable as a dependency. SI units everywhere: no guessing whether a function wants kilometers. Planned remark: "SI everywhere. The range from the campus station to G09 over its whole pass. The two epochs differ in one argument: the IGS file's timestamps are GPS time, so the correct epoch says time_system=bh.GPS. The mistake, very common in practice, is building the same calendar time as UTC. brahe does exactly what it is told: a UTC label means the instant 18 seconds later, because GPS time has not taken the leap seconds since 1980. Ask: how big is the error? Wait. Click: the satellite is about 52 km from where it should be, 18 seconds of motion at roughly 2.9 km/s in the Earth-fixed frame. Click: the range error over the pass, up to about 13 km. It is smaller than the position error because only the motion along the line of sight changes the range, and it changes sign as the satellite crosses overhead. Nothing crashes and the ranges still look plausible, which is what makes this bug expensive. Planned remark: "18 seconds. GPS never took the leap seconds, which makes it the only clock in this room that has not aged since 1980."

NASA's Magnetospheric Multiscale mission flies four spacecraft in a very eccentric orbit; at apogee MMS 1 is almost 28 Earth radii out, about seven times the radius of the GPS orbits. GPS antennas point at the Earth. Up there, the only signals that reach you are the ones that spill past the Earth's limb from satellites on the far side. Drawn exactly: for one GPS satellite, the main lobe to 23.5 degrees off boresight, side lobes out to 70 degrees, and the shadow of the Earth plus 100 km of atmosphere. Ask the question and wait. Click: the replay moves MMS around the orbit and counts the GPS satellites whose line to MMS falls inside the main lobe, and inside the main or side lobes, with the Earth blocking. This is geometry only: no transmit power, gain pattern shape, path loss or receiver sensitivity. brahe's access module takes ground locations, not a second satellite, so the script computes the off-boresight angle directly from brahe states with numpy. Every sample of the orbit, plotted against distance from the Earth's center. Main lobe only: above the GPS orbits the count drops to zero or one, and four or more satellites are available only a few percent of the orbit, near perigee. Click: add the side lobes. Geometrically, four or more are always in view. That is an upper bound. The real MMS receivers did navigate this way, but the published flight results (Winternitz et al.) report that the side-lobe signals fall below the receiver's sensitivity at the highest altitudes, above roughly 17 Earth radii, so tracking there is much sparser than this plot. The 70 degree side-lobe limit is from a conference presentation (Donaldson et al., ION GNSS+ 2018), and the 23.5 degree main lobe from the GPS III space service volume specification as discussed in Donaldson et al., NAVIGATION 2020. So the answer is yes, with a careful receiver and a link budget that this plot does not include.
